# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The method

`funmixer` unmixes nested tracer/pollutant concentration observations on a river network to
recover the *source* concentration generated by each sub-basin. The method is described in
`docs/Barnes_Lipp_2024.pdf` (Barnes & Lipp 2024, *Water Resources Research*,
[10.1029/2023WR036159](https://doi.org/10.1029/2023WR036159)). Read it before making
substantive changes to the maths — it is the authority on the following, which the code mirrors
closely:

- **Forward model** (§2.2): the concentration observed at site `i` is the flux-weighted mixture of
  all upstream sources, `d_i = Σ_{j∈U_i} q_j c_j / Σ_{j∈U_i} q_j`, where `q = a·φ` (sub-basin area ×
  export rate) and `U_i` includes `i` itself.
- **Convex misfit** (§2.3, Eq. 5): `max(d_obs/d_pred, d_pred/d_obs)` — a *convex* surrogate for
  `|log(d_pred/d_obs)|`, needed because concentration data span orders of magnitude and least
  squares would over-weight the undiluted upstream samples. Implemented as `cp_log_ratio` in
  `cvxpy_extensions.py`. Undefined at zero, so zero observations must be removed or replaced by the
  caller.
- **Regularization** (§2.4, Eq. 8): the same misfit function applied between each `c_i` and the
  *geometric* mean of the observations, scaled by `λ`. There is deliberately **no** roughness /
  spatial-smoothness term (unlike Lipp et al. 2021) — no convex relative-difference term between two
  *variables* exists, and sub-basins are irregular so roughness is ill-defined. `get_roughness()`
  reports deviation from the mean, not a spatial derivative.
- **Normalization** (§3.2): areas, export rates and observations are internally divided by their
  (geometric) mean and results multiplied back afterwards. This is purely for solver numerical
  accuracy, and means units are arbitrary — anything that changes normalization changes accuracy,
  not answers.
- **Appendix A**: the linear least-squares formulation, implemented on the `LinearFunMixer` branch
  (see below).

## Architecture

Three layers, each with a distinct job:

1. **`funmixer/flow_acc_cfuncs.pyx`** (Cython/C++). Raster-scale work: `d8_to_receivers`,
   `build_ordered_list_iterative`, `accumulate_flow`, and `build_samplesite_graph`, which walks
   upstream from sink cells labelling every pixel with the sample site that uniquely drains it. Emits
   `NativeSampleNode` objects and a per-pixel `labels` array. A synthetic `ROOT_NODE_NAME`
   (`"##ROOT##"`) node collects all outlets and is stripped when the networkx graph is built.
2. **`funmixer/d8processing.py`**. GDAL I/O, D8 validation/repair (`check_d8`,
   `set_d8_boundaries_to_zero`), sample-site snapping (`snap_to_drainage`), the `D8Accumulator`
   class, and `get_sample_graph`, which is the bridge: it turns a D8 raster + sample CSV into
   `(nx.DiGraph of SampleNode, labels array)`. Edges carry a `length` attribute (downstream flow
   distance), used for first-order decay.
3. **`funmixer/network_unmixer.py`**. The optimization. `SampleNetworkUnmixer` builds the CVXPY
   problem once in `__init__` and solves it many times.

`funmixer/__init__.py` re-exports the public API; anything user-facing should be added to both the
import list and `__all__`.

### The DPP constraint (the thing most likely to break)

CVXPY *canonicalization* dominates runtime — far more than solving. Keeping the problem
**DPP** (Disciplined Parametrized Programming) is what lets observation values, export rates,
regularization strength and rate constants be changed and re-solved without recanonicalizing, which
is what makes Monte Carlo and regularization sweeps cheap. `_build_problem` asserts
`self._problem.is_dcp(dpp=True)`; if you touch `_build_primary_terms` and that assert fires, you
have introduced a parameter-times-parameter or parameter-divided-by product.

The devices used to stay DPP, all in `_build_primary_terms`:

- `ReciprocalParameter` (`cvxpy_extensions.py`) holds a parameter `p` and its reciprocal `rp` as two
  separate parameters, so division by a parameter becomes multiplication.
- Parameter-laden expressions are pinned to fresh parameter-free `cp.Variable`s via equality
  constraints (`total_tracer_flux_dummy`, `normalised_concentration_dummy`) before being reused
  downstream.
- Total flux is *not* expressed symbolically in the objective: it is evaluated numerically at solve
  time in `_set_total_flux_parameters` (which must therefore run after
  `_set_export_rate_parameters`) and fed in as a `ReciprocalParameter`.
- First-order decay is stored as `alpha = exp(-k·d)` per edge in `_site_to_alpha`, so rate constants
  `k` are DPP-compliant and changeable per-solve. **Export rates are not** in the same sense — they
  feed total flux, so changing them requires the flux parameters to be recomputed (handled inside
  `solve`).

Consequence: `solve()` must set observation → export rate → rate constant → total flux parameters in
that order.

### Graph construction order

`_build_primary_terms` iterates in **topological order** (`nx_topological_sort_with_data`) so
upstream fluxes and tracer fluxes are accumulated into each downstream node before that node is
processed. `SampleNode` is mutated in place during this traversal (`my_total_flux`,
`my_total_tracer_flux`), so building two `SampleNetworkUnmixer`s from the same graph object resets
and reuses that state.

### Solvers

`SOLVERS` in `network_unmixer.py` maps names to CVXPY kwargs. Default is `clarabel`. `ecos` needs
loosened tolerances to converge; `gurobi` requires a licence; `scip` is impractically slow. Add new
solvers there rather than passing kwargs through.

## Commands

Run everything from the repository root (examples use paths like `data/d8.asc`).

```bash
conda env create -f requirements.yaml && conda activate funmixer
pip install -e .                          # compiles the Cython extension
```

Rebuild the extension after editing `flow_acc_cfuncs.pyx`: `pip install -e .` again (or
`python setup.py build_ext --inplace`). Stale `.so`/`.c`/`.cpp` artifacts are gitignored but do
linger in `build/`.

```bash
pytest tests/random_networks_test.py                 # unit tests (Hypothesis, property-based)
pytest tests/random_networks_test.py::test_rary_network   # a single test
python3 tests/synthetic_test.py                      # end-to-end synthetic recovery + plots
python tests/runtime_benchmark.py run                # ~30 min, caches to benchmark_results.pkl
python tests/runtime_benchmark.py plot               # plot cached results
python examples/unmix_mwe.py                         # minimal working example
```

The tests are **property-based** (Hypothesis), not example-based: they generate random balanced and
R-ary networks up to 100 nodes with log-uniform concentrations and areas over two orders of
magnitude, run the forward model, invert, and assert recovery to within
`TARGET_TOLERANCE = 0.01` (1%). They are slow by design (`@settings(deadline=None)`); the
`.hypothesis/` cache is gitignored. A failure that only appears for some seeds is a real numerical
finding, not flakiness — check whether it is a solver tolerance issue before changing the tolerance.

`tests/runtime_benchmark.py` imports from `random_networks_test` by module name, so it must be
invoked as a script from the repo root (which puts `tests/` on `sys.path`), not via pytest.

Formatting: `black --line-length=100`, enforced by `.pre-commit-config.yaml`. Several files carry
`# fmt: off` / `# fmt: skip` (notably `ELEMENT_LIST`) — preserve them. The codebase is annotated for
`pyre`; `# pyre-fixme` comments are expected and should not be cleaned up incidentally.

## Data input contract

Violations of these produce confusing failures rather than clear errors, so check them first when
debugging a user's dataset:

- D8 raster in ESRI convention (powers of 2, `0` = sink) with **every boundary pixel set to 0**.
  `check_d8` verifies both; `set_d8_boundaries_to_zero` repairs the boundary.
- Sample CSV: name in column 1, x and y in columns 2 and 3 (same CRS as the raster), tracers in
  subsequent columns. Trailing whitespace in the table is a common failure.
- Sample sites must already be snapped onto the drainage network, or sub-basins come out
  unrealistically small / the network comes out disconnected. `snap_to_drainage` does this.

## The `LinearFunMixer` branch

An unmerged branch on the remote implements Appendix A of the paper as
`LinearSampleNetworkUnmixer` / `LinearFunmixerSolution` in `funmixer/linear_unmixer.py`, plus
`examples/unmix_linear_mwe.py`, `tests/linear_unmixer_test.py`,
`tests/linear_vs_nonlinear_benchmark.py` and a LaTeX derivation in `docs/linear_unmixing_note.tex`:

    https://github.com/AlexLipp/funmixer/tree/LinearFunMixer

It penalizes *absolute* rather than relative differences, which makes the mixing matrix `d = Mc`
square and invertible, so the estimator, its covariance (`C_c = R C_d R^T`) and its resolution
matrix are all available in closed form — no Monte Carlo and no CVXPY. Appropriate for tracers with
low log-variance (e.g. isotopic data); inappropriate where concentrations span orders of magnitude.
`regularization_strength` is **not** comparable between the two solvers. Note also that the branch
carries a fix to `nx_get_downstream_data` (truthiness vs `is not None`, which matters for a node
named `0`) that has not landed on `main`.

When changing shared code on `main` (`SampleNode`, `get_sample_graph`, `__init__.py`,
`plot_sweep_of_regularizer_strength`), keep this branch in mind — the linear solver reuses all of
them.
